# The Env Pipeline

How lazy107 turns a project's scripts into a working conda environment
and a job that activates it. The pipeline is four stages, each a pure
function of the project directory except the execution stage, which is
the only place commands run.

```
scripts → ANALYSIS → dependencies → GENERATION → commands → EXECUTION → env + wiring → CONSUMPTION → sbatch
```

## Stage 1 — Analysis: project scripts → dependencies

Files: `src/lazy107/core/defaults.py` (`scan_imports`, `detect_dependencies`),
`src/lazy107/core/detect.py` (entry detection).

`scan_imports(project_root)` walks the project and returns a set of pip
install names:

- **Sources**: every `*.py` file and the code cells of every `*.ipynb`
  (markdown cells are ignored). Notebook cells make a notebook-only
  project as analyzable as a script project.
- **Line parsing** (`_scan_line`): handles `import a`, `import a, b, c`
  (all names captured), `from a.b import c` (top-level module only),
  and comments stripped first.
- **Filtering**: stdlib names (via `sys.stdlib_module_names`) and the
  project's own modules (file stems + `__init__.py` parent names) are
  skipped; hidden directories (`.venv`, `.git`, ...) are never scanned.
- **Robustness**: unreadable files and non-UTF-8 files (e.g. GBK from
  Windows editors) are skipped, never fatal; BOMs are handled via
  `utf-8-sig`; a malformed notebook is skipped.
- **Name mapping** (`_pip_name`): identity by default — `import requests`
  installs `requests`. `KNOWN_PACKAGES` corrects only the genuine
  mismatches (`sklearn`→`scikit-learn`, `skimage`→`scikit-image`,
  `PIL`→`Pillow`, `cv2`→`opencv-python`, `yaml`→`PyYAML`). A wrong name
  fails the install loudly rather than silently missing in the job.
- Accepted risk: a docstring line that looks like an import causes an
  extra install, never a missing one.

`detect_dependencies(project_root)` merges four sources into one set:
pyproject.toml `dependencies` + `optional-dependencies` (first token of
each PEP 508 spec), `requirements.txt` package names, `environment.yml`
`- name` entries, and the scanned imports.

`derive_defaults(project_root)` (same file) is the resource bridge: if
the merged set intersects `GPU_PACKAGES` (torch family, tf/keras, jax,
flax), the run plan defaults to `gpu=1, cpus=4, mem=16G, time=2h`;
otherwise `gpu=0, cpus=2, mem=4G, time=1h`.

## Stage 2 — Generation: dependencies → commands

File: `src/lazy107/cluster/env.py` (`env_commands`).

`env_commands(project_root, env_name, gpu, requirements_pending)`
returns a deterministic, printable command list:

| Command | Condition |
|---|---|
| `module load miniconda/py312` | always (no-op if conda is on PATH) |
| `conda create -y -n <env> python=3.12` | always (skipped at execution time when the env exists) |
| `conda env update -n <env> -f environment.yml` | `environment.yml` present |
| `conda run -n <env> pip install -r requirements.txt` | `requirements.txt` present (or `requirements_pending` preview) |
| `conda run -n <env> pip install -e .` | only when no `requirements.txt` but `pyproject.toml` present |
| GPU overrides (below) | `gpu > 0` and deps intersect the relevant family |

**GPU overrides** (`_gpu_overrides`) guarantee CUDA builds, because a
conda-channel torch is CPU-only and a default `jax` is CPU-only:

- torch family in deps → `pip install torch torchvision` (PyPI wheel
  bundles CUDA)
- jax/jaxlib in deps → `pip install "jax[cuda12]"`
- tensorflow/keras in deps → `pip install tensorflow` (PyPI wheel is
  GPU-enabled)

`requirements_pending` makes the dry-run preview accurate: `cmd_env`
passes it when it is about to autowrite `requirements.txt`, so the
preview shows the pip step that would run, without writing anything.

## Stage 3 — Execution: commands → env + wiring

File: `src/lazy107/cli.py` (`cmd_env`). The only stage with side effects.

1. **Env name** — `--name` if given, else the sanitized project dir name
   (`env_name_for`); both go through `sanitize_env_name`
   (`[A-Za-z0-9_.-]`, invalid chars become `_`), which also guarantees
   the name is safe for TOML and shell.
2. **Autowrite** — when imports were scanned and neither
   `requirements.txt` nor `pyproject.toml` exists, the scanned set is
   written to `requirements.txt` with a `# generated by lazy107 env`
   header (user-editable afterwards).
3. **Preview gate** — `--dry-run` prints `# would write ...` /
   `# would set conda_env ...` lines plus the command list and exits
   without touching anything.
4. **Safety gate** — without `--yes`, execution is refused.
5. **Conda discovery** — `find_conda()` (PATH, then `~/miniconda3`);
   missing conda is a hard error.
6. **Idempotency** — `env_exists` (via `conda env list --json`, 30 s
   timeout) drops the `conda create` step for existing envs; re-running
   `env --yes` only re-applies the pip steps.
7. **Run loop** — each command runs under `bash -lc` with a 900 s
   timeout; any non-zero exit or timeout aborts with the command named.
8. **GPU verification** (fail closed) — for `gpu > 0` projects whose
   deps include the torch family: `gpu_build_check` prints
   `torch.version.cuda` from inside the env; a CPU-only build (`""`) or
   a missing torch (`None`) is a hard error with a reinstall hint.
   jax/tf projects skip the torch-specific check.
9. **Wiring** — when the plan has no `conda_env`, `wire_conda_env`
   writes `conda_env = "<env>"` into `107.toml` (creates a minimal file
   if absent, replaces the empty `config --init` template line, never
   overwrites a non-empty value). A mismatch with an already-set
   `conda_env` prints a note instead.

## Stage 4 — Consumption: env → job

Files: `src/lazy107/core/render.py`, `cli.py` (`cmd_submit`),
`src/lazy107/core/validate.py`.

- **Activation block** (`_conda_block`): `set +u` guard, then
  `source "$(conda info --base)/etc/profile.d/conda.sh"` +
  `conda activate <env>` before `set -u`; omitted entirely when
  `conda_env` is unset.
- **Runtime CUDA guard** (`_GPU_GUARD`): a `find_spec('torch')` +
  `assert torch.cuda.is_available()` heredoc aborts GPU jobs that would
  silently train on CPU; jax/tf jobs skip it because the assert is
  torch-specific.
- **Submit preflight** (`cmd_submit`): `slurm_check` (partition exists)
  and `submission_check` (account/partition/qos/time/mem association)
  fail closed before rendering; a GPU plan re-checks
  `gpu_build_check` + `gpu_preflight_error` (CPU-only build blocks
  submission). When an env exists but `conda_env` is unset, submit
  prints a non-blocking warning naming the fix (`lazy107 env --yes`).

## Guarantees and failure modes

| Silent-failure risk | Where it is caught |
|---|---|
| Missing dependency (unscanned import) | `scan_imports` identity fallback; wrong names fail the install loudly |
| Comma import `import a, b` misses `b` | `_scan_line` captures every name |
| GBK/undecodable file bricks every command | skipped per-file, never fatal |
| Conda-channel CPU torch in a GPU job | pip overrides install PyPI CUDA wheels; `gpu_build_check` fails closed |
| torch not installed at all | `env --yes` fails when torch-family deps exist; job-side guard + loud import error otherwise |
| Env never activated (unwired `conda_env`) | `env --yes` wires it; submit warns when an env exists but is unwired |
| CPU training with CUDA missing in the allocation | runtime `_GPU_GUARD` assert aborts the job |
| Preview lies about what will run | `requirements_pending` makes dry-run command-accurate without writes |

## Extension points

- New import/pip mismatches: add a line to `KNOWN_PACKAGES`.
- New GPU framework: add to `GPU_PACKAGES` (resource inference), to
  `_gpu_overrides` (CUDA build), and — if torch-like — to
  `TORCH_PACKAGES` (build verification).
- New dependency manifest format: add a reader in `defaults.py` and a
  line in `detect_dependencies` + `env_commands`.
