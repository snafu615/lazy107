# lazy107 Runbook — From Zero to a Verified Run

This is the acceptance-test manual: detailed steps, verification points, and
known blockers for the cluster-only, conda-only design.

## Environment assumptions

| Item | Expected |
|---|---|
| Login node | 107 login node or Web Shell, bash shell |
| Tool install | `pip install -e .` or wheel; `lazy107 --version` works |
| conda | `module load miniconda/py312` (documented platform module) |
| Project | scaffolded with `lazy107 init`, or an existing project with an entry file |
| Code/data on cluster | git clone and/or GUI upload (see `lazy107 transfer`) |

## Step 1: Install and self-check

```bash
pip install -e .
lazy107 --version
lazy107 --help        # lists all 13 subcommands
```

Verify: version matches the checkout; help lists `init, plan, render, env,
submit, watch, status, logs, debug, transfer, discover, config, check`.

## Step 1.5: Discover your account's partition/QoS (one-time)

```bash
lazy107 discover --dry-run   # print what it resolved, write nothing
lazy107 discover             # write ~/.config/lazy107/config.toml
```

Verify (acceptance point):

- [ ] prints `account=`, `partition=`, `qos=` from `sacctmgr`/`scontrol`
- [ ] writes `~/.config/lazy107/config.toml` with the three values
- [ ] `lazy107 config` reports `global: ... (present)`
- [ ] on a machine without `sacctmgr`, it fails with a readable message

This is the fix for "Invalid account or account/partition combination
specified": the tool's built-in default (`Students`/`qos_stu_default`) is
not authorized for competition accounts; `discover` resolves the right
account/partition/QoS from the live Slurm association.

## Step 2: Scaffold a project

```bash
lazy107 init demo
cd demo
```

Verify (acceptance point):

- [ ] `src/__init__.py`, `src/data.py`, `src/model.py`, `src/train.py` exist
- [ ] `pyproject.toml` names the project and depends on `torch`
- [ ] `environment.yml` has `name: demo`, `python=3.12`, `pip`
- [ ] `scripts/train.sbatch` is a valid reference script with conda activation
- [ ] `.gitignore` ignores data/outputs/logs/checkpoints/models + large suffixes

Edit `src/train.py` to a minimal training loop, or leave the `NotImplementedError`
stubs and use `--dry-run` only (no submission needed for steps 3-5).

## Step 3: Environment preparation

```bash
lazy107 env --dry-run
```

Verify (acceptance point):

- [ ] First line is `module load miniconda/py312` (with a "no-op if conda
      already on PATH" comment)
- [ ] `conda create -y -n demo python=3.12` present
- [ ] torch project → a pip install (PyPI default wheel bundles CUDA);
      **no** conda-channel install is the final step
- [ ] bare `lazy107 env` (no `--yes`) fails with "use --yes to execute" —
      `env` never runs installs without an explicit `--yes`

For a code-only project (only `.py` files, no `pyproject.toml` /
`requirements.txt` / `environment.yml`):

- [ ] `env --dry-run` prints `# would write requirements.txt (imports: ...)`
      and a command list that includes
      `pip install -r requirements.txt` (the post-write sequence)
- [ ] every non-stdlib, non-local import becomes a pip package in the
      preview (identity fallback; `sklearn` shows as `scikit-learn` etc.)
- [ ] `env --dry-run` writes nothing (no `requirements.txt` created)
- [ ] `lazy107 plan` infers `gpu=1` when the code imports torch

If conda is available on the login node, run for real:

```bash
lazy107 env --yes
```

Verify:

- [ ] env `demo` exists (`conda env list`)
- [ ] re-running `env --yes` skips the create step (idempotent)
- [ ] code-only project: `env --yes` wrote `requirements.txt` (header
      `# generated by lazy107 env`) before installing
- [ ] without `conda_env` in `107.toml`, `env --yes` writes
      `conda_env = "demo"` into 107.toml (minimal file created if absent);
      re-running keeps it
- [ ] if torch is installed: `conda run -n demo python -c "import torch; print(torch.version.cuda)"`
      prints a CUDA version — **non-empty is the required proof**;
      `torch.cuda.is_available()` is expected `False` on the login node and
      proves nothing

## Step 4: Plan and render

```bash
lazy107 plan
```

Verify (acceptance point):

- [ ] `entry=src/train.py` (nested detection works)
- [ ] `gpu=1`, `cpus=4`, `mem=16G`, `time=2:00:00` (torch inferred)
- [ ] `account=` present (empty until `discover` or `107.toml` sets it)
- [ ] no `107.toml` yet → defaults apply

```bash
lazy107 render --dry-run
```

Verify (acceptance point):

- [ ] `--partition=Students`, `--qos=qos_stu_default`, `--cpus-per-task=4`,
      `--mem=16G`, `--time=2:00:00`, `--nodes=1`, `%x_%j` logs
- [ ] `--gres=gpu:1` present **and** the CUDA runtime assertion block present
- [ ] conda block absent when `conda_env` is unset — run `env --yes`
      (which wires it) or set `conda_env` in `107.toml` to see it appear
- [ ] `--dry-run` wrote **nothing** (no `scripts/train.sbatch`)

## Step 5: Configuration layers

```bash
lazy107 config --init
```

Verify (acceptance point):

- [ ] `107.toml` created; `lazy107 config` shows `manifest: ... (present)`
- [ ] editing `gpu = 0` changes `lazy107 plan` to `gpu=0` **and** removes
      `--gres` + the CUDA guard from the render
- [ ] `LAZY107_GPU=2 lazy107 plan` overrides the manifest; a CLI flag
      overrides the env var
- [ ] deleting `107.toml` restores inference defaults

## Step 6: Transfer checklist

```bash
lazy107 transfer
```

Verify (acceptance point):

- [ ] fresh project → `No large files found; nothing to transfer.`
- [ ] after adding `data/raw.bin` → lists it, prints a `tar -czf` command
      with quoted paths, a GUI upload note, extraction command, and
      `sha256sum`
- [ ] nothing is executed — output only

## Step 7: Submit and monitor (needs a real entry + env)

```bash
lazy107 submit --dry-run --yes
lazy107 submit --yes
```

Verify (acceptance point):

- [ ] dry-run prints the script and writes nothing
- [ ] without `--yes` the confirmation prompt is honored (`n` aborts)
- [ ] success prints `submitted job <job_id>` and a `watch` hint
- [ ] `notes/runs.md` contains `## Job <job_id>` with entry, partition, QoS
- [ ] `lazy107 watch <job_id>` prints `scontrol show job <job_id>`,
      `squeue --me`, `tail -f logs/<job_name>_<job_id>.out`
      and `tail -f logs/<job_name>_<job_id>.err`
- [ ] job reaches `R` and completes; logs land in `logs/`
- [ ] on failure, `lazy107 debug <job_id>` prints a cause and fix (or the
      exit-code fallback when logs are empty)

## Common blockers

### 1. `env` fails: conda not found

`module load miniconda/py312` first, or install Miniconda under `~/miniconda3`.
The tool prints this exact hint.

### 2. GPU job blocked: CPU-only torch

The env has a CPU torch build (e.g. from conda-forge or a CPU index). Fix:
`lazy107 env --yes` (PyPI wheel bundles CUDA). If a conda channel is
required, pin `pytorch-cuda=12.6` (or `13.0`) explicitly.

### 3. `render`/`submit` fails: entry not found

The detected or `--entry` file does not exist. `lazy107` resolves and
validates the entry path before doing anything else.

### 4. Submit blocked: partition preflight

`sinfo -p <partition> -h` failed. Check the name in `107.toml`; use
`--skip-check` only if you know the partition is fine.

### 4b. Submit blocked: account/QoS not allowed

Preflight queries `sacctmgr`/`scontrol` and blocks with a message naming the
problem (`account X is not allowed on partition Y` or `qos X is not allowed
on partition Y`) plus a hint. Fix: `lazy107 discover`, or set
`account`/`partition`/`qos` in `107.toml`. This is the actionable version of
Slurm's `Invalid account or account/partition combination specified` sbatch
error.

### 5. Job runs but trains on CPU despite `gpu>0`

The runtime CUDA assertion in the generated sbatch aborts the job with
`GPU requested but CUDA unavailable in this job`. That means the **env**
build was fine but something else (e.g. `CUDA_VISIBLE_DEVICES` or a stale
environment override) hid the GPU. Check `nvidia-smi` inside the job.

### 6. `notes/runs.md` missing after submit

Only successful submissions are recorded. Check the submit output for
errors; the job ID is printed before recording, so a record failure would
be visible.
